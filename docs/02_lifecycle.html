Lifecycle de Execução

Do início de um thread LangGraph até sua conclusão — incluindo detecção de falha, retomada automática do checkpoint e dead-letter queue para threads irrecuperáveis.

Contexto

O problema que o lifecycle resolve

O LangGraph com RedisSaver persiste o estado do grafo no Redis a cada checkpoint. Isso resolve a durabilidade do estado — mas não resolve o problema de orquestração: quem sabe que um thread estava em execução quando o ECS task morreu? E quem retoma?

O ECS é efêmero por natureza — spot interruptions, deploys, OOM kills. Sem um mecanismo explícito de lifecycle, threads ficam em estado "zumbi": o checkpoint existe no Redis, mas nenhum processo sabe que precisa continuar.

Sem lifecycle: Thread thread-123 está em execução na Task v1 └─► ECS mata o task (spot interruption) └─► Checkpoint do node_a está no Redis ✓ └─► node_b estava executando — checkpoint parcial ou ausente ✗ └─► Nenhum processo sabe que thread-123 precisa ser retomado └─► Thread fica "zumbi" — nem rodando, nem com erro explícito Com lifecycle: Task morre → heartbeat expira em 30s └─► OrphanScanner detecta ausência do heartbeat → enfileira └─► RecoveryConsumer retoma: ainvoke(None, thread_id) └─► LangGraph lê checkpoint → continua do último nó salvo
Visão geral

Arquitetura dos componentes

O sistema é composto por quatro componentes que se comunicam exclusivamente via Redis. Nenhum componente fala diretamente com outro processo — o estado é o intermediário.

ComponenteResponsabilidadeLoopOnde roda
AgentHeartbeatAnuncia que o thread está vivoa cada 10sDentro do Agent Task
OrphanScannerDetecta threads sem heartbeata cada 20sRecovery Worker (ECS)

Por que o Recovery Worker não fala com o Agent Task

É um equívoco imaginar que o worker precisaria "avisar" o agente. O processo morreu — não há como comunicar. O estado vive no Redis, não no processo. O Recovery Worker apenas lê o checkpoint e reexecuta o grafo — sem comunicação inter-processo. O ECS task morto é irrelevante para a retomada.

Estrutura de dados

TTL de 24h no contador de tentativas

O contador recovery:attempts:{thread_id} tem TTL de 24h. Isso evita que uma falha passada impeça recovery futura se o problema foi corrigido — o contador reseta automaticamente, sem intervenção manual.

Componente 1

Heartbeat

O heartbeat é um mecanismo de presença passiva: o processo não precisa fazer nada além de renovar uma chave Redis com TTL curto. Se o processo morre, simplesmente para de renovar. O TTL faz o trabalho de expirar a chave.

Por que TTL 30s e renovação a cada 10s

A janela de 3x entre renovação (10s) e TTL (30s) garante que flutuações de latência ou GC pauses não causem falsos positivos. Se o processo está vivo mas lento, o heartbeat ainda vai expirar dentro de 30s sem renovação. Se o processo morreu, a chave expira em no máximo 30s — janela máxima de invisibilidade de um órfão.

Implementação

pythonagent_runner.py
import asyncio
import redis.asyncio as aioredis
from contextlib import asynccontextmanager

HEARTBEAT_TTL      = 30   # segundos — TTL da chave no Redis
HEARTBEAT_INTERVAL = 10   # segundos — frequência de renovação


class AgentHeartbeat:
    def __init__(self, redis: aioredis.Redis, thread_id: str, task_id: str):
        self.redis     = redis
        self.thread_id = thread_id
        self.task_id   = task_id
        self._key      = f"heartbeat:{thread_id}"

    async def _beat(self):
        # SETEX: SET + EX atômico.
        # Valor = task_id (identifica qual ECS task está rodando o thread).
        # Útil para debug: saber qual task foi responsável por um thread.
        await self.redis.setex(self._key, HEARTBEAT_TTL, self.task_id)

    @asynccontextmanager
    async def running(self):
        # Loop de heartbeat em background — roda enquanto o grafo executa.
        # asyncio.create_task cria uma corrotina independente no mesmo event loop.
        async def loop():
            while True:
                await self._beat()
                await asyncio.sleep(HEARTBEAT_INTERVAL)

        task = asyncio.create_task(loop())
        try:
            await self._beat()  # bate imediatamente — não espera 10s
            yield
        finally:
            task.cancel()
            # Limpa ao terminar normalmente — OrphanScanner não vai ver este thread
            await self.redis.delete(self._key)


async def run_agent(thread_id: str, input: dict, ecs_task_id: str):
    # Registra no set de threads em andamento
    await redis.sadd("threads:in_progress", thread_id)

    heartbeat = AgentHeartbeat(redis, thread_id, ecs_task_id)

    async with heartbeat.running():
        result = await graph.ainvoke(
            input,
            config={"configurable": {"thread_id": thread_id}},
        )

    # Remove do set ao terminar normalmente
    await redis.srem("threads:in_progress", thread_id)
    return result
Componente 2

OrphanScanner

O scanner varre periodicamente o set threads:in_progress e verifica se a chave de heartbeat existe para cada thread_id. A ausência do heartbeat — combinada com a presença no set — é a definição de órfão.

Falso positivo: thread terminou normalmente mas scan aconteceu antes da limpeza

Existe uma janela de race condition: o grafo terminou, srem ainda não executou, o scanner roda. O RecoveryConsumer trata isso verificando state.next antes de retomar — se o grafo está em estado terminal, simplesmente ignora e limpa o registro.

Implementação

pythonrecovery_worker.py — OrphanScanner
class OrphanScanner:
    def __init__(self, redis: aioredis.Redis):
        self.redis = redis

    async def scan_once(self) -> list[str]:
        # SMEMBERS: retorna todos os thread_ids em andamento.
        # Para conjuntos grandes, considere SSCAN com cursor para não bloquear o Redis.
        thread_ids: set[str] = await self.redis.smembers("threads:in_progress")

        if not thread_ids:
            return []

        orphans = []
        for thread_id in thread_ids:
            heartbeat_key = f"heartbeat:{thread_id}"
            alive = await self.redis.exists(heartbeat_key)
            if not alive:
                orphans.append(thread_id)

        return orphans

    async def enqueue_orphans(self, orphans: list[str], guard: QueueGuard) -> None:
        for thread_id in orphans:
            # Verifica se já está na fila — idempotência do enqueue
            already = await self.redis.lpos("recovery:queue", thread_id)
            if already is not None:
                logger.info("Thread %s já na fila, pulando.", thread_id)
                continue

            # Remove do in_progress antes de enfileirar
            await self.redis.srem("threads:in_progress", thread_id)
            enqueued = await guard.safe_enqueue(thread_id)

            if enqueued:
                logger.warning("Órfão enfileirado: %s", thread_id)
            # se não enfileirado: QueueGuard mandou para DLQ (fila cheia)

    async def run(self, guard: QueueGuard) -> None:
        logger.info("OrphanScanner iniciado (intervalo=20s)")
        while True:
            try:
                orphans = await self.scan_once()
                if orphans:
                    logger.info("%d órfão(s): %s", len(orphans), orphans)
                    await self.enqueue_orphans(orphans, guard)
            except Exception:
                logger.exception("Erro no OrphanScanner")
            await asyncio.sleep(20)
Componente 3

Como ainvoke(None) retoma o grafo

Este é o mecanismo central do recovery e vale entender em profundidade. Quando ainvoke é chamado com None como input e um thread_id existente no config, o LangGraph não começa um novo grafo — ele lê o último checkpoint do RedisSaver e continua a partir dos nós pendentes (state.next).

graph.ainvoke(None, config={"configurable": {"thread_id": "thread-123"}}) │ ▼ RedisSaver.get(thread_id="thread-123") └─► lê último checkpoint do Redis └─► deserializa: state.values + state.next + state.metadata │ ▼ state.next = ("booking_agent",) ← nós pendentes │ ▼ LangGraph executa apenas os nós em state.next └─► booking_agent_node(state, config) └─► salva novo checkpoint após cada nó └─► atualiza state.next com os próximos nós │ ▼ state.next = () ← estado terminal └─► ainvoke retorna o estado final
Por que o input é None e não o estado anterior

O estado já está no checkpoint — passar o estado como input seria redundante e potencialmente conflitante. None significa "use o estado do checkpoint, não adicione novo input". Se você passar um input não-None, o LangGraph vai mesclar com o estado existente — útil para retomadas com novo input do usuário, mas não para recovery transparente.

RecoveryConsumer — implementação completa

pythonrecovery_worker.py — RecoveryConsumer
class RecoveryConsumer:
    def __init__(self, redis, graph, dlq: "DLQManager"):
        self.redis = redis
        self.graph = graph
        self.dlq   = dlq

    async def consume_one(self, thread_id: str) -> None:
        langgraph_config = {"configurable": {"thread_id": thread_id}}
        logger.info("Iniciando retomada: %s", thread_id)

        try:
            # Lê o estado atual antes de retomar.
            # Isso permite verificar se vale a pena tentar — evita timeout desnecessário.
            state = await self.graph.aget_state(langgraph_config)

            if not state:
                # Checkpoint não existe — reenfileirar não vai resolver.
                # Vai direto para DLQ sem gastar tentativas.
                await self.dlq.send_to_dlq(
                    thread_id, reason="no_checkpoint",
                    error="aget_state() retornou vazio — checkpoint ausente ou expirado",
                )
                return

            if not state.next:
                # Estado terminal — provavelmente falso positivo do scanner.
                # Limpa o contador de tentativas se existir.
                logger.info("Thread %s em estado terminal. Ignorando.", thread_id)
                await self.redis.delete(f"recovery:attempts:{thread_id}")
                return

            logger.info("Retomando %s nos nós: %s", thread_id, list(state.next))

            # wait_for garante que não ficamos presos além do timeout.
            # Se exceder, lança asyncio.TimeoutError — tratado abaixo.
            await asyncio.wait_for(
                self.graph.ainvoke(None, config=langgraph_config),
                timeout=120,
            )

            # Sucesso — limpa o contador de tentativas
            await self.redis.delete(f"recovery:attempts:{thread_id}")
            logger.info("Thread %s retomado com sucesso.", thread_id)

        except asyncio.TimeoutError:
            await self.dlq.handle_failure(
                thread_id, reason="timeout",
                error="Execução excedeu 120s",
            )
        except Exception as exc:
            await self.dlq.handle_failure(
                thread_id, reason="exception", error=str(exc),
            )

    async def run(self) -> None:
        logger.info("RecoveryConsumer iniciado.")
        while True:
            try:
                # BLPOP: bloqueia até ter item na fila.
                # timeout=5 evita que fique travado para sempre — retorna None se timeout.
                # Preferível a polling com sleep porque não desperdiça CPU.
                result = await self.redis.blpop("recovery:queue", timeout=5)
                if result is None:
                    continue  # fila vazia — volta ao início do loop

                _, thread_id = result  # result = ("recovery:queue", "thread-123")
                await self.consume_one(thread_id)

            except Exception:
                logger.exception("Erro no RecoveryConsumer.run()")
                await asyncio.sleep(1)
Componente 4

Dead-Letter Queue

Sem DLQ, um thread que falha consistentemente — checkpoint corrompido, nó com bug, API permanentemente down — reentra na fila indefinidamente. O sistema gasta recursos em algo que nunca vai funcionar, e o operador não tem visibilidade do problema.

O DLQManager mantém um contador de tentativas por thread_id com TTL de 24h. Após MAX_ATTEMPTS falhas, o thread vai para a DLQ com metadados completos para diagnóstico.

Dois caminhos distintos para a DLQ

handle_failure(): para erros recuperáveis (timeout, exception). Conta tentativas e decide entre reenfileirar ou DLQ. send_to_dlq() direto: para erros irrecuperáveis como checkpoint ausente. Reenfileirar não vai resolver — vai direto para DLQ sem gastar o contador.

DLQManager — implementação

pythonrecovery_worker.py — DLQManager
import json
from datetime import datetime, timezone

MAX_ATTEMPTS  = int(os.getenv("RECOVERY_MAX_ATTEMPTS", "3"))
ATTEMPTS_TTL  = 60 * 60 * 24  # 24h — reseta automaticamente


class DLQManager:
    def __init__(self, redis):
        self.redis = redis

    async def get_attempts(self, thread_id: str) -> int:
        val = await self.redis.get(f"recovery:attempts:{thread_id}")
        return int(val) if val else 0

    async def increment_attempts(self, thread_id: str) -> int:
        key      = f"recovery:attempts:{thread_id}"
        attempts = await self.redis.incr(key)
        if attempts == 1:
            # Primeira falha — define TTL para o contador não acumular para sempre.
            # INCR não aceita EX — precisa de EXPIRE separado.
            await self.redis.expire(key, ATTEMPTS_TTL)
        return attempts

    async def send_to_dlq(self, thread_id: str, reason: str, error: str = "") -> None:
        attempts = await self.get_attempts(thread_id)
        meta = {
            "thread_id": thread_id,
            "reason":    reason,
            "error":     error[:500],  # trunca para não poluir o Redis
            "attempts":  str(attempts),
            "failed_at": datetime.now(timezone.utc).isoformat(),
        }
        pipe = self.redis.pipeline()
        pipe.rpush("recovery:dlq", thread_id)
        pipe.hset(f"recovery:dlq:meta:{thread_id}", mapping=meta)
        pipe.delete(f"recovery:attempts:{thread_id}")
        await pipe.execute()

        logger.error("Thread %s → DLQ após %d tentativas. reason=%s error=%s",
                     thread_id, attempts, reason, error[:200])

    async def handle_failure(self, thread_id: str, reason: str, error: str = "") -> None:
        """Ponto central de decisão após falha de recovery."""
        attempts  = await self.increment_attempts(thread_id)
        remaining = MAX_ATTEMPTS - attempts

        if attempts >= MAX_ATTEMPTS:
            await self.send_to_dlq(thread_id, reason=reason, error=error)
        else:
            logger.warning("Thread %s falhou (tentativa %d/%d). %d restante(s).",
                           thread_id, attempts, MAX_ATTEMPTS, remaining)
            await self.redis.rpush("recovery:queue", thread_id)

    async def list_dlq(self) -> list[dict]:
        """Retorna todos os itens da DLQ com metadados. Para inspeção/dashboards."""
        thread_ids = await self.redis.lrange("recovery:dlq", 0, -1)
        result = []
        for tid in thread_ids:
            meta = await self.redis.hgetall(f"recovery:dlq:meta:{tid}")
            result.append(meta or {"thread_id": tid})
        return result

Requeue manual da DLQ

Após identificar e corrigir o problema que causou as falhas — bug no nó, API externa down, schema incompatível — o operador pode mover threads de volta para a fila principal.

pythonrecovery_worker.py — DLQManager.requeue_from_dlq
async def requeue_from_dlq(self, thread_id: str) -> bool:
    """Remove da DLQ e reenfileira para nova tentativa.
    Use após corrigir o problema — o contador é resetado."""
    pos = await self.redis.lpos("recovery:dlq", thread_id)
    if pos is None:
        logger.warning("Thread %s não encontrado na DLQ.", thread_id)
        return False

    # Pipeline atômico: remove da DLQ, limpa meta, reseta contador, reenfileira
    pipe = self.redis.pipeline()
    pipe.lrem("recovery:dlq", 1, thread_id)
    pipe.delete(f"recovery:dlq:meta:{thread_id}")
    pipe.delete(f"recovery:attempts:{thread_id}")
    pipe.rpush("recovery:queue", thread_id)
    await pipe.execute()

    logger.info("Thread %s removido da DLQ e reenfileirado.", thread_id)
    return True

Graceful shutdown — respeitando o SIGTERM

O ECS envia SIGTERM antes de matar o container. O agente precisa honrar esse sinal: parar de aceitar novos requests e aguardar os requests em andamento terminarem. Sem isso, threads são interrompidos no meio — exatamente o problema que o lifecycle resolve.

pythonapp.py — lifespan
from contextlib import asynccontextmanager
from fastapi import FastAPI

_active_tasks: set[asyncio.Task] = set()
_shutting_down = False


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
    # Shutdown: recusa novos requests e aguarda tasks ativas.
    # ECS dá stop_timeout segundos antes do SIGKILL — configurado em 120s.
    global _shutting_down
    _shutting_down = True

    if _active_tasks:
        logger.info("Aguardando %d task(s) ativas...", len(_active_tasks))
        # timeout=25 deixa margem para overhead do shutdown
        await asyncio.wait(_active_tasks, timeout=25.0)

    logger.info("Shutdown completo.")


app = FastAPI(lifespan=lifespan)


@app.post("/agents/invoke")
async def invoke(body: InvokeRequest):
    if _shutting_down:
        raise HTTPException(status_code=503, detail="Serviço em manutenção.")

    task = asyncio.current_task()
    _active_tasks.add(task)
    try:
        return await run_agent(body.thread_id, body.input, ecs_task_id)
    finally:
        _active_tasks.discard(task)
