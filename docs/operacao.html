Contexto

O problema específico com checkpoints ativos

Deploy em ECS sem checkpoints é simples: sobe nova versão, drena a antiga. Com LangGraph + RedisSaver, existe uma complicação: threads podem estar em execução no momento do deploy. Se o ECS task for drenado no meio de uma execução, o checkpoint do estado intermediário está no Redis — mas ninguém sabe que o thread precisa ser retomado até o heartbeat expirar e o OrphanScanner detectar.

Sem graceful shutdown:
Thread thread-123 está em execução na Task v1 — node_b executando
  └─► Deploy inicia → ECS drena Task v1 → SIGTERM
  └─► Processo recebe SIGTERM → Python não trata → processo termina imediatamente
  └─► node_b: checkpoint anterior (node_a) está no Redis ✓
  └─► node_b em execução: sem checkpoint salvo ✗
  └─► Recovery Worker precisa retomar — mas leva até 50s para detectar

Com graceful shutdown + stop_timeout adequado:
SIGTERM recebido → FastAPI para de aceitar novos requests
  └─► Aguarda tasks ativas terminarem (até 25s)
  └─► node_b termina normalmente → checkpoint salvo
  └─► Heartbeat deletado → OrphanScanner não detecta como órfão
  └─► Deploy continua sem recovery necessário
Por que o graceful shutdown é pré-requisito de qualquer estratégia de deploy

Blue/Green, Canary e Rolling são estratégias de quando trocar o tráfego. Graceful shutdown resolve o que acontece com os requests em andamento no momento da troca. Sem ele, todas as três estratégias ainda causam interrupções para threads LangGraph que estavam executando.

Pré-requisito

Graceful shutdown correto

app.py — lifespan + shutdown python 
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
import asyncio

_active_tasks: set[asyncio.Task] = set()
_shutting_down = False


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
    global _shutting_down
    _shutting_down = True

    if _active_tasks:
        logger.info("Aguardando %d task(s) ativas...", len(_active_tasks))
        # timeout=25 deixa margem para overhead — stop_timeout do ECS deve ser 120s
        await asyncio.wait(_active_tasks, timeout=25.0)

    logger.info("Shutdown completo.")


app = FastAPI(lifespan=lifespan)


@app.post("/agents/invoke")
async def invoke(body: InvokeRequest):
    if _shutting_down:
        # 503 durante shutdown — ALB vai retentar em outro target
        raise HTTPException(status_code=503, detail="Serviço em manutenção.")

    task = asyncio.current_task()
    _active_tasks.add(task)
    try:
        return await run_agent(body.thread_id, body.input)
    finally:
        _active_tasks.discard(task)
terraform — stop_timeout e deregistration_delay hcl 
# stop_timeout: segundos que o ECS aguarda após SIGTERM antes de SIGKILL
# Deve ser >= tempo máximo de execução de um agente (ex: 120s para booking)
resource "aws_ecs_task_definition" "agent" {
  container_definitions = jsonencode([{
    name        = "agent"
    stopTimeout = 120
    # ... demais configs
  }])
}

# deregistration_delay: tempo que o ALB aguarda antes de remover o target
# Permite que connections existentes terminem antes de drenar
# Deve ser ligeiramente menor que stop_timeout
resource "aws_lb_target_group" "agent" {
  deregistration_delay = 100
  health_check {
    path                = "/health"
    healthy_threshold   = 2
    unhealthy_threshold = 3
    interval            = 10
  }
}
Estratégia 1

Blue/Green com CodeDeploy

O CodeDeploy gerencia dois Target Groups — BLUE (versão atual) e GREEN (nova versão). O tráfego de produção continua 100% no BLUE enquanto o GREEN aquece, passa nos health checks, e é validado por smoke tests. A troca é instantânea — uma mudança de peso no ALB listener.

ALB Listener :443
  └─► Production rule → Target Group BLUE (100%) ← tráfego atual

Deploy inicia:
  1. CodeDeploy sobe Tasks GREEN (v2) → health checks passam
  2. Smoke tests via test listener (porta :8080) → validam GREEN diretamente
  3. CodeDeploy troca: ALB → Target Group GREEN (100%)
  4. Tasks BLUE recebem SIGTERM → graceful shutdown (até 120s)
  5. Deploy finalizado — BLUE descartado

Em caso de falha:
  └─► CodeDeploy reverte: ALB → BLUE (instantâneo — zero downtime)

Terraform — dois Target Groups

terraform/blue_green.tf hcl 
# ECS Service com deployment_controller CODE_DEPLOY
resource "aws_ecs_service" "agent" {
  name            = "booking-agent"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.agent.arn
  desired_count   = 3

  deployment_controller {
    type = "CODE_DEPLOY"  # entrega o controle de deploy ao CodeDeploy
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.blue.arn
    container_name   = "agent"
    container_port   = 8000
  }

  # lifecycle: impede que o Terraform gerencie o target group após o primeiro deploy
  # CodeDeploy é quem alterna entre BLUE e GREEN
  lifecycle {
    ignore_changes = [task_definition, load_balancer]
  }
}

# Target Group BLUE — versão atual
resource "aws_lb_target_group" "blue" {
  name                 = "agent-blue"
  port                 = 8000
  protocol             = "HTTP"
  vpc_id               = var.vpc_id
  target_type          = "ip"
  deregistration_delay = 100
  health_check { path = "/health"; interval = 10; healthy_threshold = 2 }
}

# Target Group GREEN — nova versão (inicialmente vazio)
resource "aws_lb_target_group" "green" {
  name                 = "agent-green"
  port                 = 8000
  protocol             = "HTTP"
  vpc_id               = var.vpc_id
  target_type          = "ip"
  deregistration_delay = 100
  health_check { path = "/health"; interval = 10; healthy_threshold = 2 }
}

# Listener de produção: tráfego real → BLUE (CodeDeploy alterna para GREEN)
resource "aws_lb_listener" "prod" {
  load_balancer_arn = aws_lb.main.arn
  port              = 443; protocol = "HTTPS"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.blue.arn
  }
}

# Listener de teste: smoke tests acessam GREEN diretamente antes da troca
resource "aws_lb_listener" "test" {
  load_balancer_arn = aws_lb.main.arn
  port              = 8080; protocol = "HTTP"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.green.arn
  }
}

# CodeDeploy deployment group
resource "aws_codedeploy_deployment_group" "agent" {
  app_name              = aws_codedeploy_app.agent.name
  deployment_group_name = "booking-agent-dg"
  service_role_arn      = aws_iam_role.codedeploy.arn

  deployment_config_name = "CodeDeployDefault.ECSAllAtOnce"

  ecs_service {
    cluster_name = aws_ecs_cluster.main.name
    service_name = aws_ecs_service.agent.name
  }

  load_balancer_info {
    target_group_pair_info {
      prod_traffic_route { listener_arns = [aws_lb_listener.prod.arn] }
      test_traffic_route { listener_arns = [aws_lb_listener.test.arn] }
      target_group { name = aws_lb_target_group.blue.name  }
      target_group { name = aws_lb_target_group.green.name }
    }
  }

  auto_rollback_configuration {
    enabled = true
    events  = ["DEPLOYMENT_FAILURE", "DEPLOYMENT_STOP_ON_ALARM"]
  }
}

AppSpec e hooks

appspec.yml yaml 
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: "<TASK_DEFINITION>"
        LoadBalancerInfo:
          ContainerName: "agent"
          ContainerPort: 8000

Hooks:
  # BeforeAllowTraffic: roda ANTES de trocar o tráfego para GREEN
  # Ideal para smoke tests — valida a nova versão sem expor ao usuário
  - BeforeAllowTraffic: "BeforeTrafficHook"

  # AfterAllowTraffic: roda DEPOIS da troca — monitora métricas por N minutos
  # Se alarmes dispararem aqui, CodeDeploy reverte para BLUE automaticamente
  - AfterAllowTraffic: "AfterTrafficHook"
hooks/before_traffic.py — smoke tests python 
import httpx, sys

# Hook roda contra o test listener (porta 8080) — acessa GREEN diretamente
# antes de qualquer tráfego de usuário chegar à nova versão
TEST_ENDPOINT = "http://alb-dns:8080"


def run_smoke_tests():
    checks = [
        ("/health",             200),
        ("/health/circuit-breakers", 200),
        ("/health/bulkheads",   200),
    ]
    for path, expected_status in checks:
        resp = httpx.get(f"{TEST_ENDPOINT}{path}", timeout=10)
        if resp.status_code != expected_status:
            print(f"FAIL: {path} returned {resp.status_code}, expected {expected_status}")
            sys.exit(1)
        print(f"OK: {path} → {resp.status_code}")

    print("Smoke tests passed. Permitindo tráfego para GREEN.")


if __name__ == "__main__":
    run_smoke_tests()
Estratégia 2

Canary — weighted routing progressivo

Em vez de trocar 100% do tráfego de uma vez, o Canary envia uma fração pequena (10%) para a nova versão enquanto monitora métricas. Se algo der errado, o rollback acontece automaticamente via CloudWatch Alarms — sem intervenção manual.

ALB Listener :443 — Canary em andamento
  ├─► 90% → Target Group BLUE  (v1) ← tráfego principal
  └─► 10% → Target Group GREEN (v2) ← canary

Após estabilidade confirmada (CloudWatch Alarms OK por N minutos):
  └─► CodeDeploy progressão: 25% → 50% → 75% → 100%
  └─► Tasks BLUE drenadas gradualmente

Se alarme disparar durante o canary:
  └─► CodeDeploy rollback automático: 100% → BLUE
  └─► Tasks GREEN descartadas
  └─► Sem intervenção manual necessária

Rollback automático via CloudWatch Alarms

terraform/canary.tf hcl 
# Alarme de error rate — dispara se > 10 erros 5xx por minuto
resource "aws_cloudwatch_metric_alarm" "error_rate" {
  alarm_name          = "agent-5xx-canary"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "HTTPCode_Target_5XX_Count"
  namespace           = "AWS/ApplicationELB"
  period              = 60
  statistic           = "Sum"
  threshold           = 10
  alarm_description   = "Canary rollback trigger: 5xx rate"

  dimensions = {
    LoadBalancer = aws_lb.main.arn_suffix
  }
}

# Alarme de latência P99 — dispara se > 3s
resource "aws_cloudwatch_metric_alarm" "p99_latency" {
  alarm_name          = "agent-p99-canary"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "TargetResponseTime"
  namespace           = "AWS/ApplicationELB"
  period              = 60
  extended_statistic  = "p99"
  threshold           = 3
}

# CodeDeploy deployment group com canary e rollback por alarme
resource "aws_codedeploy_deployment_group" "agent_canary" {
  deployment_config_name = "CodeDeployDefault.ECSCanary10Percent5Minutes"
  # Alternativas:
  # ECSCanary10Percent5Minutes  → 10% por 5min, depois 100%
  # ECSLinear10PercentEvery1Minutes → 10% por minuto até 100%

  auto_rollback_configuration {
    enabled = true
    events  = ["DEPLOYMENT_FAILURE", "DEPLOYMENT_STOP_ON_ALARM"]
  }

  alarm_configuration {
    alarms  = [aws_cloudwatch_metric_alarm.error_rate.name,
               aws_cloudwatch_metric_alarm.p99_latency.name]
    enabled = true
  }
}

Estratégia 3

Rolling Update — ECS nativo

O ECS substitui tasks gradualmente sem CodeDeploy ou Target Group duplicado. Mais simples de operar, menor custo — mas sem smoke tests pré-tráfego e rollback mais lento (depende do circuit breaker nativo do ECS detectar falhas).

desired_count=3, maximum_percent=150%, minimum_healthy_percent=100%

Estado inicial:  [v1] [v1] [v1]
Passo 1:         [v1] [v1] [v1] [v2]    ← sobe v2 (150% capacity)
Passo 2:         [v1] [v1] [v2]         ← drena 1 v1 após v2 passar no health check
Passo 3:         [v1] [v2] [v2]         ← sobe mais 1 v2, drena 1 v1
Passo 4:         [v2] [v2] [v2]         ← completo

Em nenhum momento: capacity < 100% (minimum_healthy_percent=100)

Circuit breaker de deploy

terraform/rolling.tf hcl 
resource "aws_ecs_service" "agent" {
  deployment_controller { type = "ECS" }  # rolling nativo

  # deployment_circuit_breaker: rollback automático se health checks falharem
  # durante o rolling. Evita que uma versão quebrada continue sendo deployada.
  deployment_circuit_breaker {
    enable   = true
    rollback = true
  }

  # maximum_percent=150: pode ter até 4 tasks durante o deploy (3 * 1.5)
  # minimum_healthy_percent=100: nunca fica abaixo de 3 tasks saudáveis
  deployment_maximum_percent         = 150
  deployment_minimum_healthy_percent = 100
}
Limitação do Rolling para multi-cluster

O Rolling Update não oferece controle explícito da ordem de deploy entre clusters. Se você tem booking-agent e search-agent em clusters separados com um contrato A2A evoluindo, o Rolling pode deployar os dois em ordens imprevisíveis. Para breaking changes A2A entre clusters, use Blue/Green com sequência manual controlada.

Multi-cluster

O problema de ordem em multi-cluster

Quando agentes em clusters diferentes evoluem o schema do estado A2A, a ordem de deploy importa. Se você deploya o produtor (search-agent v2 com novo formato de resposta) antes do consumidor (booking-agent v2 que sabe interpretar o novo formato), o booking-agent v1 ainda em produção vai receber respostas v2 que não sabe processar.

Ordem errada:
  1. Deploy search-agent v2  ← agora responde com formato v2
  2. booking-agent v1 chama search-agent v2
  3. booking-agent v1 recebe resposta v2 que não sabe parsear → erro

Ordem correta — consumidor antes do produtor:
  1. Deploy booking-agent v2  ← aceita tanto v1 quanto v2 de resposta
  2. Valida booking-agent v2 estável (15-30min de métricas)
  3. Deploy search-agent v2   ← agora pode responder com v2
  4. booking-agent v2 processa v2 corretamente ✓
  5. Após estável: deploy search-agent v2.1 remove suporte a v1

Versionamento de contrato A2A

Durante a janela de migração, o search-agent v2 precisa responder em ambos os formatos. O header X-API-Version permite que o booking-agent sinalize qual versão espera receber.

a2a_client.py — versionamento de contrato python 
async def call_search_agent(payload: dict, token: str) -> dict:
    headers = {
        "Authorization":   f"Bearer {token}",
        "X-API-Version":   "v2",   # versão do contrato que esperamos
        "X-Min-API-Version": "v1", # versão mínima que aceitamos
    }
    inject(headers)
    async with httpx.AsyncClient() as client:
        return (await client.post(endpoint, json=payload, headers=headers)).json()
app.py — search-agent v2 com backward compat python 
@app.post("/search/invoke")
async def search_invoke(request: Request, body: SearchRequest):
    requested_version = request.headers.get("X-API-Version", "v1")
    result = await run_search_graph(body)

    # Suporta v1 e v2 durante a janela de migração.
    # Após booking-agent v2 estável, remova o branch v1.
    if requested_version == "v1":
        return format_response_v1(result)
    return format_response_v2(result)

Sequência completa de deploy multi-cluster

.github/workflows/deploy.yml — multi-cluster yaml 
jobs:
  deploy-booking-agent-v2:
    # Consumidor primeiro — aceita v1 e v2 de resposta
    steps:
      - name: Deploy booking-agent v2
        run: aws deploy create-deployment --deployment-group booking-agent-dg ...

      - name: Aguarda estabilização (15min)
        run: sleep 900

      - name: Valida métricas do booking-agent v2
        run: python scripts/validate_metrics.py --service booking-agent --window 15m

  deploy-search-agent-v2:
    needs: deploy-booking-agent-v2  # só roda após o consumidor estável
    # Produtor depois — agora pode responder com v2
    steps:
      - name: Deploy search-agent v2
        run: aws deploy create-deployment --deployment-group search-agent-dg ...

      - name: Aguarda estabilização (15min)
        run: sleep 900

  remove-v1-compat:
    needs: deploy-search-agent-v2
    # Remove suporte a v1 apenas quando ambos estão em v2
    steps:
      - name: Deploy search-agent v2.1 (sem compat v1)
        run: aws deploy create-deployment --deployment-group search-agent-dg ...

NLB vs ALB

CaracterísticaALBNLB
ProtocoloHTTP/HTTPS/WebSocketTCP/UDP/TLS

Recomendação para o sistema multi-agent

ALB externo (usuário → agente): weighted routing, Blue/Green via CodeDeploy, header-based routing para canary por usuário beta. NLB interno (agente → agente via A2A): menor latência, gRPC direto quando aplicável. Blue/Green no NLB interno: via DNS swap no Route 53 (CNAME de search-agent.internal para o novo target group).
