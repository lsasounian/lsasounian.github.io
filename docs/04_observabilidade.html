Contexto

O desafio em multi-agent

Em um sistema single-agent, um trace cobre um processo. Em multi-agent, um único request do usuário pode atravessar três ou quatro agentes em ECS tasks diferentes. Sem propagação explícita de contexto, você tem logs isolados por agente — impossível correlacionar o que aconteceu em um request específico.

Request do usuário (trace_id: abc123) │ ▼ [booking-agent] POST /invoke 2.3s trace_id=abc123 ├── langgraph.node.router 0.1s ├── langgraph.node.search_hotels 0.4s ├── langgraph.node.book_hotel 1.1s │ └── HTTP POST api.hotels.com/bookings 0.9s └── [search-agent] A2A call 0.8s trace_id=abc123 ← mesmo trace! ├── langgraph.node.search_flights 0.5s └── langgraph.node.format_results 0.3s Sem propagação: dois traces separados — impossível correlacionar Com W3C TraceContext: uma árvore unificada no X-Ray

Setup

TracerProvider

O TracerProvider é configurado uma vez no startup da aplicação e registrado globalmente. Todos os módulos que precisam criar spans importam o tracer global — não instanciam um TracerProvider próprio.

pythonobservability.py
import os
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace.sampling import ParentBased, TraceIdRatioBased

SERVICE_NAME  = os.getenv("SERVICE_NAME",  "agent-service")
OTLP_ENDPOINT = os.getenv("OTLP_ENDPOINT", "http://localhost:4317")
SAMPLE_RATE   = float(os.getenv("TRACE_SAMPLE_RATE", "1.0"))


def setup_tracing() -> trace.Tracer:
    resource = Resource.create({
        "service.name":         SERVICE_NAME,
        "service.version":      os.getenv("APP_VERSION", "unknown"),
        "deployment.environment": os.getenv("ENVIRONMENT", "dev"),
        # Esses atributos aparecem em todos os spans deste serviço no X-Ray
    })

    # ParentBased: se vier de um pai que já foi sampleado, segue a decisão.
    # Crítico em multi-agent: garante que toda a cadeia A2A tem o mesmo
    # comportamento de sampling — ou todos os agentes capturam, ou nenhum.
    sampler = ParentBased(root=TraceIdRatioBased(SAMPLE_RATE))

    provider = TracerProvider(resource=resource, sampler=sampler)
    exporter = OTLPSpanExporter(endpoint=OTLP_ENDPOINT, insecure=True)
    # BatchSpanProcessor: acumula spans e envia em lotes — mais eficiente que SimpleSpanProcessor
    provider.add_span_processor(BatchSpanProcessor(exporter))

    trace.set_tracer_provider(provider)
    return trace.get_tracer(SERVICE_NAME)


# Tracer global — importado por todos os módulos que criam spans
tracer = setup_tracing()

FastAPI + HTTPX — instrumentação automática

pythonapp.py
from fastapi import FastAPI
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from opentelemetry.instrumentation.httpx import HTTPXClientInstrumentor
from observability import tracer

app = FastAPI()

# FastAPIInstrumentor: cria root span para cada request HTTP automaticamente.
# Lê o header traceparent se presente — continua o trace do chamador.
# Sem isso, cada request começa um trace novo sem contexto do pai.
FastAPIInstrumentor.instrument_app(app)

# HTTPXClientInstrumentor: injeta traceparent em TODAS as chamadas httpx saindo deste agente.
# Isso cobre automaticamente chamadas A2A via httpx — sem código adicional por request.
# Também funciona com httpx.AsyncClient instanciado dentro de funções.
HTTPXClientInstrumentor().instrument()
Por que instrumentar o HTTPX e não fazer inject() manual

O HTTPXClientInstrumentor injeta o traceparent em todas as chamadas httpx automaticamente, sem modificar o código dos clients. Se você fizer inject() manual, precisa lembrar de fazer isso em cada ponto de chamada — e esquecer um quebra a cadeia de trace. A instrumentação automática é à prova de esquecimento.

Spans LangGraph

Decorator @traced_node

O LangGraph não tem instrumentação nativa de OpenTelemetry. O decorator @traced_node cria um span filho para cada nó, herdando o span pai do request HTTP via contexto de thread. Erros são capturados e anotados no span antes de re-propagar.

pythonobservability.py — traced_node
from functools import wraps
from opentelemetry import trace
from opentelemetry.trace import SpanKind, Status, StatusCode


def traced_node(node_name: str, attributes: dict | None = None):
    def decorator(func):
        @wraps(func)
        async def wrapper(state: dict, config: dict, *args, **kwargs):
            thread_id = config.get("configurable", {}).get("thread_id", "unknown")

            # start_as_current_span: cria o span e o define como current no contexto.
            # Spans filhos criados dentro desta função herdarão este como pai.
            # kind=INTERNAL: não é uma chamada HTTP recebida nem enviada — é processamento interno.
            with tracer.start_as_current_span(
                f"langgraph.node.{node_name}",
                kind=SpanKind.INTERNAL,
            ) as span:
                span.set_attribute("langgraph.node",      node_name)
                span.set_attribute("langgraph.thread_id", thread_id)

                # Atributos extras definidos no decorator — ex: {"agent.capability": "booking"}
                if attributes:
                    for k, v in attributes.items():
                        span.set_attribute(k, str(v))

                try:
                    result = await func(state, config, *args, **kwargs)

                    # Anota campos escalares do resultado — visíveis no X-Ray trace
                    if isinstance(result, dict):
                        for k, v in result.items():
                            if isinstance(v, (str, int, float, bool)):
                                span.set_attribute(f"langgraph.output.{k}", v)

                    span.set_status(Status(StatusCode.OK))
                    return result

                except Exception as exc:
                    # record_exception: captura stack trace no span — visível no X-Ray
                    # set_status ERROR: marca o span como falho — filtráveis no console
                    span.record_exception(exc)
                    span.set_status(Status(StatusCode.ERROR, str(exc)))
                    raise

        return wrapper
    return decorator

Composição com outros decorators

A ordem dos decorators define qual envolve qual. @traced_node deve ficar por fora para capturar o tempo total — incluindo o check de idempotência e a execução real.

pythonnodes.py
# Ordem de aplicação (de fora para dentro):
# 1. traced_node    → cria o span, captura tempo total + erros
# 2. idempotent_node → verifica cache; se hit, retorna sem chamar a função real
# 3. função real    → executa a ação externa

# O span do traced_node captura o tempo do idempotency check também.
# Se for cache hit, o span vai aparecer com duração muito baixa — sinal visual útil.

@traced_node("book_hotel", attributes={"agent.capability": "booking"})
@idempotent_node(redis, "book_hotel", key_fields=["hotel_id", "checkin"])
async def book_hotel_node(state: AgentState, config: dict) -> dict:
    return await with_retry(
        hotel_api.create_booking,
        hotel_id=state["hotel_id"],
        config=RETRY_CONFIGS["hotel_api"],
        circuit_breaker=circuit_registry.get("hotel_api"),
        service_name="hotel_api",
    )
Propagação A2A

W3C TraceContext — o header traceparent

O padrão W3C TraceContext define o header traceparent no formato 00-{trace_id}-{parent_span_id}-{flags}. Quando o Agente B recebe esse header e cria spans dentro do mesmo trace_id, o X-Ray exibe tudo como uma única árvore.

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 ↑ ↑ ↑ ↑ | trace_id (128 bits, hex) parent_span_id flags (01=sampled) version
Por que W3C TraceContext e não X-Ray trace header nativo

O X-Ray usa seu próprio formato de header (X-Amzn-Trace-Id). O W3C TraceContext (traceparent) é o padrão aberto suportado por OpenTelemetry, Jaeger, Zipkin e outros. Usar o padrão aberto significa que você pode trocar o backend de traces (X-Ray → Grafana Tempo, por exemplo) sem alterar o código de propagação.

inject() e extract() — propagação manual

O HTTPXClientInstrumentor faz isso automaticamente para chamadas httpx. Mas em chamadas A2A com autenticação JWT (headers customizados), vale entender o mecanismo para garantir que o traceparent não é sobrescrito.

pythona2a_client.py
import httpx
from opentelemetry.propagate import inject
from token_manager import token_manager


async def call_search_agent(endpoint: str, payload: dict) -> dict:
    token = await token_manager.get_token()

    headers = {
        "Authorization": f"Bearer {token}",
        "Content-Type":  "application/json",
    }

    # inject() adiciona traceparent (e tracestate se presente) ao dict de headers.
    # Modifica headers in-place — o dict já tem o JWT, inject adiciona o trace context.
    # HTTPXClientInstrumentor também faz isso automaticamente, mas inject() explícito
    # garante que o contexto está correto mesmo se o instrutor não estiver ativo.
    inject(headers)

    async with httpx.AsyncClient() as client:
        response = await client.post(
            endpoint, json=payload, headers=headers,
            timeout=remaining_budget(),  # cascading timeout budget
        )
        response.raise_for_status()
        return response.json()

Recebimento e continuação no Agente B

pythonapp.py — Agente B
from opentelemetry.propagate import extract
from opentelemetry import trace
from opentelemetry.trace import SpanKind

# FastAPIInstrumentor faz o extract() automaticamente — o span raiz do Agente B
# já herda o trace_id do Agente A sem código adicional.
# O trecho abaixo mostra o que acontece internamente:

@app.post("/search/invoke")
async def search_invoke(request: Request, body: SearchRequest):
    # extract() lê o traceparent do header e cria um SpanContext com o trace_id do Agente A
    ctx = extract(dict(request.headers))

    # start_as_current_span com context=ctx: este span é filho do span do Agente A.
    # Mesmo trace_id → mesma árvore no X-Ray.
    with tracer.start_as_current_span(
        "search_agent.invoke",
        context=ctx,
        kind=SpanKind.SERVER,
    ) as span:
        span.set_attribute("agent.name",         "search-agent")
        span.set_attribute("langgraph.thread_id", body.thread_id)
        return await run_search_graph(body)
Sampling

ParentBased — decisão unificada na cadeia A2A

Em multi-agent, a decisão de sampling precisa ser consistente: se o Agente A samplea um trace, todos os agentes na cadeia devem capturar aquele trace. O ParentBased garante isso: se o span pai foi sampleado, o filho segue — independente do ratio local.

AmbienteSamplerRatioComportamento
devTraceIdRatioBased1.0100% — visibilidade total para debug
stagingParentBased(Ratio)0.550% com consistência na cadeia A2A
prod baixo volumeParentBased(Ratio)0.110% — custo aceitável de armazenamento
prod alto volumeErrorAwareSampler0.011% normal + 100% em erros

ErrorAwareSampler — sempre captura erros

pythonobservability.py — ErrorAwareSampler
from opentelemetry.sdk.trace.sampling import (
    Sampler, SamplingResult, Decision, TraceIdRatioBased, ParentBased
)
from opentelemetry.trace import SpanContext


class ErrorAwareSampler(Sampler):
    """
    Samplea 1% do tráfego normal, mas sempre captura traces com erro.
    Útil em prod alto volume: visibilidade nos problemas sem custo de 100% de traces.
    """

    def __init__(self, ratio: float):
        self._ratio = TraceIdRatioBased(ratio)

    def should_sample(self, parent_context, trace_id, name, kind, attributes, links):
        # Se vier de um pai já sampleado (cadeia A2A), segue a decisão do pai
        parent_span = trace.get_current_span(parent_context)
        if parent_span and parent_span.is_recording():
            return SamplingResult(Decision.RECORD_AND_SAMPLE)

        # Verifica se o span atual tem atributo de erro (definido antes do sampling)
        if attributes and attributes.get("error"):
            return SamplingResult(Decision.RECORD_AND_SAMPLE)

        return self._ratio.should_sample(parent_context, trace_id, name, kind, attributes, links)

    def get_description(self) -> str:
        return "ErrorAwareSampler"
Infraestrutura

Sidecar X-Ray Daemon no ECS

O X-Ray Daemon roda como container sidecar no mesmo task — acessível via localhost:4317. Recebe spans via OTLP gRPC do agente e os repassa para a API do X-Ray. A vantagem do sidecar é que não há configuração de rede especial — containers no mesmo task compartilham o network namespace.

hclterraform/task_definition.tf
container_definitions = jsonencode([
  {
    name    = "agent"
    image   = "${aws_ecr_repository.app.repository_url}:latest"
    command = ["python", "app.py"]
    environment = [
      { name = "OTLP_ENDPOINT",    value = "http://localhost:4317" },
      { name = "SERVICE_NAME",     value = "booking-agent" },
      { name = "TRACE_SAMPLE_RATE", value = "0.1" },
    ]
  },
  {
    name  = "xray-daemon"
    image = "amazon/aws-xray-daemon:latest"
    portMappings = [
      # Porta 4317: OTLP gRPC — recebe spans do agente
      { containerPort = 4317, protocol = "tcp" },
      # Porta 2000: X-Ray nativo UDP — para AWS SDK legado
      { containerPort = 2000, protocol = "udp" },
    ]
    # Sem hostPort: só acessível via localhost dentro do task
  }
])

Métricas estruturadas — CloudWatch Logs Insights

Além de traces, o QueueMonitor emite métricas operacionais como JSON estruturado. O CloudWatch Logs Insights parseia automaticamente campos JSON — é possível criar dashboards e alarmes sem código adicional.

pythonrecovery_worker.py — QueueMonitor
class QueueMonitor:
    async def run(self) -> None:
        while True:
            try:
                metrics = {
                    "recovery_queue_size":        await self.redis.llen("recovery:queue"),
                    "recovery_queue_max":         QUEUE_MAX_SIZE,
                    "recovery_queue_utilization": await self._utilization(),
                    "dlq_size":                   await self.redis.llen("recovery:dlq"),
                    "threads_in_progress":        await self.redis.scard("threads:in_progress"),
                }
                # JSON no log — Logs Insights parseia e indexa cada campo automaticamente
                logger.info("METRICS %s", json.dumps(metrics))

                if metrics["dlq_size"] > 0:
                    logger.error("DLQ contém %d item(ns). Intervenção necessária.",
                                 metrics["dlq_size"])
            except Exception:
                logger.exception("Erro no QueueMonitor")
            await asyncio.sleep(30)

# CloudWatch Logs Insights — queries úteis:
# fields @timestamp, recovery_queue_size, dlq_size
# | filter ispresent(recovery_queue_size)
# | sort @timestamp desc
# | limit 100

# Alarme: recovery_queue_size > 80 → WARNING
# Alarme: dlq_size > 0             → CRITICAL (intervenção manual)
